# `assessment.md` — target refs, topic tests, the mistake index and placement

Authored 2026-09-10 for **W23** of [`research/reports/APP_PLAN.md`](../research/reports/APP_PLAN.md).
Closes the readiness gaps that make the assessment *system* absent while the in-lesson quiz layer looks
green: `tests_exercises` **G3** (no placement), **G4** (no topic test), **G6** (an exercise cannot say
what it tests), **G12** (no state model for attempts), and `jlpt_course_path` **G11** (no placement, no
checkpoints, no progression semantics).

**This document is design only.** It edits no contract and no schema. Every fragment below is a
*proposal* stated exactly enough that the DB-writer unit can apply it mechanically:
`contracts/lesson.schema.json` is generated by `scripts/contracts/build_schemas.py` from
`contracts/_shapes.json`, so the exercise change lands as a `SHAPE_BY_PATH` entry plus an exporter
change, never as a hand edit to the generated file. The hand-authored `contracts/user_state/*` files
and the new `contracts/topic_test.schema.json` are written by that unit, from §3–§5 here.

**Where this document and the manifest, the enums or `user_state.md` disagree, they win and this file
is the bug** — the same rule `api_contract.md` opens with.

**Language.** Design prose and every identifier, key and enum value are neutral English
([`i18n.md`](i18n.md)). Only learner-facing strings are pt-BR, and the examples below show them as
`LocaleText` objects.

**Level-agnostic (spec §1.6).** Nothing here hardcodes a level set. A topic test is addressed by its
topic, the mistake index by item stable id, placement by the prerequisite graph. Adding N2/N1 is adding
rows.

## 1. The four things, and why they are one unit

An exercise cannot say what it tests. That single missing edge is why there is no mistake index (nothing
to key it on), no topic test (nothing to assemble a keyed test *about a topic* from), and no placement
(a probe that cannot say which item it probed cannot map a score onto a lesson). `item_refs` is the
field the other three stand on, so it is §2 and everything else follows it.

| # | what | layer | address | new? |
|---|---|---|---|---|
| 1 | `item_refs[]` on `lesson.exercises[]` and on `exam_item` | content (B where derived, C where authored) | none — a field | field on two entities |
| 2 | `topic_test` | content (C) | `test:<topic-slug>` | **new content entity** |
| 3 | `exercise_attempt` + the `mistake_index` view | runtime | `xat:<opaque>` | **new runtime entity**, plus a view with no table |
| 4 | `assessment_attempt`, `course/item_lesson_index.json` | runtime + generated index | `asm:<opaque>-<n>` | **new runtime entity**, one generated map |

Everything else these four need already exists: `cumulative_known_set`, the unlock ledger, `needs[]`,
`lesson_progress.cards_seeded`, `card.tags`, the exam banks, the sentence bank.

## 2. `item_refs` — what an exercise tests

### 2.1 The field

`item_refs` already exists in the **authoring** source (`research/derived/lessons/*.json`), is loaded
into the `exercise_item` link table (`scripts/ingest/load_lessons.py`, `001_init.sql`), is migrated by
`migrate_grammar_merge.py`, and is **empty on all 2,463 exercises**. The exporter never emits it
(`export_course.py` builds the exercise dict from five keys), so it is absent from every published
lesson and from the generated contract. This unit fills it, emits it and gates it.

**Name collision, stated once so nobody trips on it:** `course/gating_exemptions.json` has a top-level
array *also* called `item_refs`, holding lesson-body refs held by `validate_lesson_gating` check B.
Different thing entirely. The new exemption file in §2.5 is therefore `course/item_ref_exemptions.json`
and its array is called `exercises`, not `item_refs`.

**Entry shape.** Four fields, no more:

| field | type | nullable | meaning |
|---|---|---|---|
| `type` | string, design enum | no | which registry the ref addresses |
| `ref` | `IdRef` | no | the published stable id of the item |
| `role` | string, enum `target` \| `context` | no | `target` = a wrong answer is evidence about *this* item; `context` = the item is present but is not what the question asks |
| `derived_by` | string | no | the rule that produced the entry — the audit trail, and what a re-derivation compares against |

`role` is explicit rather than defaulted because the whole value of the field is the distinction it
carries; a defaulted `target` would silently promote scaffolding. **This pass populates `target` only.**
`context` is legal and empty, on the precedent of `card.kind: listening` (contracted, zero rows, blocked
on a later unit). The measured cost of turning it on is in §2.4.

**`derived_by` values**, closed by this document:

| value | meaning |
|---|---|
| `table:practice_kanji_exercises` | the row came from `research/derived/repairs/practice_kanji_exercises.json` |
| `table:practice_vocab_exercises` | from `research/derived/pending/practice_vocab_exercises.json` |
| `markup` | a `<vocab ref>` / `<kanji ref>` / `<grammar ref>` in the prompt named it |
| `answer` | the answer-key surfaces named it (§2.2 rule 2) |
| `prompt-unlocks` | the prompt's Japanese named it and this lesson unlocks it (rule 3) |
| `cited-sentence` | the exercise's own `sentence_refs` dissection named it (rule 4) |
| `kana` | the kana rule (rule 5) |
| `authored` | a human or an Opus residue pass wrote it; no rule produced it |

### 2.2 The derivation rule, in order

The matcher is **not a new one**. `scripts/validate/validate_practice_coverage.py` already implements
the "does this exercise target this item" question — MaxMatch tiling over the full vocab surface set
with the kana-boundary filter, plain character containment for kanji, placeholder-split probe segments
for grammar, and the rule that an answer string which *is* a cited sentence is read through that
sentence's Layer-A dissection rather than re-tiled. The derivation script **imports that module** and
reuses `load_vocab`, `load_kanji`, `load_grammar`, `make_tiler`, `answer_surfaces`, `fold_sentence` and
`TARGET_REF_RX` verbatim. Two definitions of "practised" that drift apart is exactly the defect this
field exists to remove.

What is new is that the matcher runs **per exercise** instead of pooled per lesson, and that the credit
is scoped. Rules apply in order; each adds refs, and rule 6 narrows what survives.

**Rule 0 — a table wins.** If the exercise id appears in a tracked table that declares `targets`, those
refs are the `target` set, `derived_by: table:<name>`, and rules 1–6 do not run. This covers 3,210 of the
4,774 exercises (899 applied kanji rows + 2,311 generated vocab/grammar rows) by construction. It is
first because the tables *are* the ground truth: they were generated with the target in hand, and §2.4
measures how often re-derivation fails to recover it.

**Rule 1 — explicit markup wins over everything derived.** Any `<vocab ref=…>` / `<kanji ref=…>` /
`<grammar ref=…>` inside the `prompt` locale object is a `target`, `derived_by: markup`. Zero exercises
carry such markup today; the branch exists because the authoring path can, and `validate_practice_coverage`
already reads it.

**Rule 2 — the answer surfaces, per type.** Only the strings the learner must produce or that are marked
correct. Distractors are never read: a word that appears only as a wrong option is being discriminated
against incidentally.

| exercise `type` | the strings rule 2 reads | `derived_by` |
|---|---|---|
| `cloze` | `answer.text` (the filler); `answer.full` when `text` is empty | `answer` |
| `production`, `handwriting` | `answer.text` | `answer` |
| `recognition`, `reading`, `listening`, `particle_choice` | `answer.correct` | `answer` |
| `sentence_build`, `ordering` | `answer.text` (the assembled sentence) | `answer` |
| `matching` | both members of every `answer.pairs[]` row — a matching grid has no wrong content | `answer` |

From those strings: vocab by MaxMatch tiling, kanji by character containment, grammar by probe-segment
containment (a one-character segment such as も / の / は matches only when a whole answer string *is*
that character). Every hit is intersected with the lesson's `cumulative_known_set` for its kind, so an
exercise can never target an item the course has not taught by that point.

**Rule 3 — the prompt, narrowed to this lesson's own unlocks.** Union in every item the prompt's Japanese
names *that this lesson unlocks*. `derived_by: prompt-unlocks`.

This is the one rule that departs from `validate_practice_coverage`, which excludes incidental prompt
Japanese on the grounds that the stem of "Complete: 私＿学生です。" is scaffolding. That reasoning is right
for a coverage gate and wrong for a target index, because **the largest single class of exercise in the
corpus puts its target in the prompt and its answer in kana**: "Na contagem japonesa, como se lê o kanji
一?" answers いち. Measured on the 899 kanji exercises whose true target is known, adding rule 3 moves
recovery from **719 to 785 of 899**. The intersection with *this lesson's unlocks* is what bounds the
noise: 私 and 学生 in the stem above are not unlocked by that lesson, so they never enter.

**Rule 4 — the cited sentence.** If rules 2–3 produced nothing and `sentence_refs` names a bank sentence,
take that sentence's own dissection (token `vocab` slugs, `grammar[]` tags, token surface characters),
intersected with the known set, narrowed to the lesson's unlocks when that intersection is non-empty.
`derived_by: cited-sentence`. Fires on 12 exercises.

**Rule 5 — kana.** If rules 1–4 produced nothing *and* the lesson unlocks kana families, tile the answer
strings and the prompt against the kana glyph registry **longest-match first**, and map every
`'ryo'`-style romaji token quoted in the prompt through the same registry, keeping only glyphs whose
family this lesson unlocks. `derived_by: kana`. Fires on 118 exercises, all pre-N5.

Longest-match is load-bearing and not decoration: `corpus/kana/hiragana.json` holds 105 records of which
**33 are yōon digraphs** (`kana:hiragana-しゃ`, `kana:hiragana-りょ`), and ゃ/ゅ/ょ are not records of
their own. A per-character rule reads しゃ as し plus nothing and leaves the whole contracted-sound half
of pre-N5 — `les:pre-n5-hiragana-14/15`, `les:pre-n5-katakana-14` — in the residue. Measured: the
per-character version leaves 74 exercises without a target, the longest-match version 64.

**Rule 6 — the narrowing.** If the accumulated set intersects the lesson's own `unlocks`, the
intersection is the `target` set and the remainder is `context`. *An exercise inside a lesson is about
what that lesson teaches.* This is what turns containment into targeting: measured over the 2,463
exported exercises, without rule 6 the mean is **4.32 refs per exercise and the maximum 32** (a
`sentence_build` answer credits every word and kanji in the sentence); with it, **mean 1.50, median 1,
p90 3, max 22**.

### 2.3 `type`, and the kana granularity

`item_refs[].type` is a **new design-owned enum** added to
[`design/unlock_enums.json`](unlock_enums.json) as `item_ref_type`:

```
["vocab", "kanji", "grammar", "kana", "conjugation-form", "phrase"]
```

It is `unlock_type` minus `{kanji-family, feature, srs-deck}` — an exercise tests an item, never a
grouping, an app feature or a deck — with `kana-family` renamed to `kana`, for one reason worth stating.
The unlock taxonomy calls it `kana-family` because `_kana_ref_note` in `unlock_enums.json` says only
families are unlockable. But a test target legitimately *is* one glyph: "Escreva o hiragana do som 'o'"
targets お, not the whole あ row. So `type: "kana"` accepts **both** granularities —
`kana:hiragana-a` (family) and `kana:hiragana-お` (glyph) — which is the same ruling `card.item` already
carries under D6, for the same reason: the target state is one glyph per fact, and the contract has to
hold across the W29 migration.

`conjugation-form` and `phrase` are in the enum and will have zero rows until W22 creates
`conjugation-form` unlocks (today: 0 across all 322 lessons, and `cumulative_known_set` carries the key
empty on every one). Level-agnostic and future-proof beats a closed set that has to be widened.

**Fan-out.** Hand-authored: mean 1.77 target refs, median 1, p90 4, max 22. Table rows: mean 1.19,

and the 4% is not random: it is the kanji-reading shape whose answer is a kana reading that tiles onto a
*vocab* record (`ex:n5-convites-04-6` answers きく; the table says `kanji:聞`, the derivation says
`vocab:1591110`, and both are arguably present — one is what the item asks). This is why rule 0 exists,
why `derived_by` is on every entry, and why the Fable sample for this unit reads **30 rows with
`derived_by: answer` or `prompt-unlocks` against the exercise as rendered**, not against the JSON.

on the precedent of `"lesson.srs.introduces_cards[].production_key"` (W27). The generated
`contracts/lesson.schema.json` then carries, inside `properties.exercises.items.properties`:

```json
{

    "items": {
      "type": "object",

```

`item_refs` itself is **required on every exercise** and may be an empty array only under the exemption
file; the exercise object stays `additionalProperties: false`, which is what makes the addition a
deliberate design edit rather than a data accident.

**One shared `$def`, so three entities cannot drift.** The entry object above is added to
`contracts/common.schema.json#/$defs` as **`ItemRef`**, with `type`, `ref` and `role` required and
`derived_by` declared but optional. `topic_test.pool[].item_refs` (§3.4) `$ref`s it directly. Two places
do not: `lesson.exercises[].item_refs` is *generated* by `build_schemas.py`, which writes the shape it is
given rather than a reference, and additionally requires `derived_by` (a corpus record must say which
rule produced it); `exercise_attempt.item_refs` (§4.4) deliberately drops `derived_by`, because a learner's
answer is not the place to re-record how the courseware decided what it was asking. Both differences are
intentional; the shared `$def` is what makes them visible as differences instead of as three
independently-typed arrays.

**Exporter change.** `export_course.py` reads `exercise_item` and emits the array sorted by
`(type, ref)` so the export is order-stable — the property W11 found missing on `unlocks[]` and
`cumulative_known_set`, which permuted 283 files with zero content change. **Ingest change.**
`load_lessons.py` must persist `role` and `derived_by`; `exercise_item` gains two columns in a
migration (`role TEXT NOT NULL DEFAULT 'target'`, `derived_by TEXT NOT NULL`) and its primary key stays
`(exercise_id, member_type, member_id)`.

**Sequencing, from W05's lesson.** After the export, regenerate the contracts *before*
`validate_contracts` — the new field is an additional property the previous contract rejects.

### 2.6 `exam_item` gets the same field, and one address-space defect it exposes

`corpus/exam_banks/*.json` holds 6,081 items. Their refs today: `vocab` 3,726 · `sentence` 3,022 ·
`grammar` 728 · `reading` 517. Two defects, both measured:

1. **No exam item carries a kanji ref**, although the 2,379 `kanji_reading` + `orthography` items *are*
   kanji tests. A mistake index over exam answers can therefore say nothing about kanji, which is the
   half of the corpus the learner is weakest on.
2. **`exam_item.grammar` holds the bare key** (`n3-sono-ue`), not the published slug (`gram:n3-sono-ue`).
   The corpus is one graph addressed by stable id (§1.7); one entity addressing grammar in key space is
   how a join silently loses 728 items, which is exactly what the readiness audit's 73.7% was.

Both are fixed by giving `exam_item` the **same `item_refs` array**, with the same enum and the same
`derived_by` vocabulary plus one value, `exam-key`, for a ref lifted from the item's own `vocab` /
`grammar` / `reading` field. Derivation for exam items:

- `vocab` → `{type: vocab, ref: <as stored, already a slug>, role: target}`;
- `grammar` → `{type: grammar, ref: "gram:" + <key>, role: target}`;
- `kanji_reading` / `orthography` → the kanji characters of the item's `target` field (364 items carry
  one) or of its `vocab` record's headword, `role: target`;
- everything else (`sentence_order`, `reading_comp`, `text_grammar`, listening) → `role: context` from
  the cited sentence's or passage's dissection, because those items test a structure, not an item.

**This belongs to W18, not to W23**: `build_exam_banks.py` is being rewritten and the banks regenerated
once (`APP_PLAN` §6 step 10), and authoring a field onto 6,081 items that are about to be regenerated is
the waste-ledger mistake. W23 owns the **shape**; W18 emits it. Until then the topic-test assembler and
the placement probe use the join in §5.1, which is the same derivation run at read time.

### 2.7 The validator: `validate_item_refs.py`

Over the exported JSON, never the SQLite. Hard checks:

| # | check | failure |
|---|---|---|
| A | every `ref` resolves to an exported record of its `type` | FAIL |
| B | every `ref` is inside the exercise's lesson `cumulative_known_set` for that kind (kana refs resolve through their family) | FAIL — this is the gating rule, per exercise |
| C | every exercise has ≥1 entry with `role: target`, **or** is listed in `course/item_ref_exemptions.json` with a non-empty reason | FAIL |
| D | the exemption file cannot rot: an entry naming no exercise, or naming an exercise that has since gained a target, is itself a FAIL | FAIL |
| E | **re-derivation.** The validator re-runs §2.2 rules 0–6 on the tree being validated and compares. A stored entry whose `derived_by` is a rule but which the rule does not reproduce is a FAIL; a stored entry with `derived_by: authored` is exempt from E by construction | FAIL |
| F | `derived_by: table:*` entries replay against the named table (the `validate_repairs_applied` join) | FAIL |

Check E is the W21 `C4` pattern — *re-derive the whole model on the tree being validated* — which caught
11 plants there. It is what stops `item_refs` from becoming a stale cache the way
`design/reading_practice.md`'s promised `reading_refs` became a field nobody wrote.

**Ratchet:** `scripts/validate/item_refs_baseline.json`, frozen at **64 exercises without a target**
(25 exempt, 39 pending authoring), per (level, type). Growth fails; shrinkage prints the ceiling to
lower. **Plant proof** required before it joins the suite, on a copied tree with the validator and its
`validate_practice_coverage` import copied in: (1) point a ref at a retired slug → A; (2) point a ref at
an item the lesson has not taught → B; (3) blank one exercise's array → C; (4) add an exemption for an
exercise that has refs → D; (5) hand-edit one derived ref to a different real item → E.

**What `validate_practice_coverage` does with the new field.** Nothing changes in its own matcher — its
branch 2 (explicit target markup) is widened to read `item_refs` as well, which was always the plan
("the branch is here so the W20 authoring campaign and a future `tests[]` ref array are measured the
moment they land"). Because the gate's own containment rule stays, the practice ratchet cannot regress
from this change; it can only find items the containment measure missed.

## 3. `topic_test` — a keyed test per topic

### 3.1 What it is and what it is not

A **blueprint**, not a sat paper and not a fixed list of questions: it publishes the *pool* a test draws
from and the *rules* the draw obeys, so a retake is a fresh sample rather than the same twelve questions.
It is Layer C (pedagogy: the size, the mix and the pass mark are judgement) and therefore
`needs_review: true` on every record, per §1.1.

Address: `test:<topic-slug-without-prefix>` — `test:n5-adjetivos` for `top:n5-adjetivos`. One per topic,
level-agnostic: nothing in the id or the schema names a level, and `level` is copied from the topic as
data.

### 3.3 Scope, size, mix, pass

**Scope** — the set of items the test may ask about. Three values, on the record:

| `scope.kind` | which topics | the set |
|---|---|---|
| `own` | 46 topics | the items this topic's lessons unlock |
| `range` | the 3 `revisao` topics | every item unlocked from the topic after the previous review topic (or the start of the level) up to this one — which is what a review topic *is*, and the only reason `top:n3-revisao` (4 own items) is testable at all |
| `none` | `top:pre-n5-orientacao`, `top:pre-n5-sons`, `top:pre-n5-pronuncia` | no test. These teach method and phonology and unlock no item; a test would be a quiz about the course. Listed in `course/test_exemptions.json` with a reason each, on the `practice_exemptions.json` pattern |

49 topics get a test. The two `kanji-exame` topics keep `own` scope: their pool is their own 35 and 56
lesson exercises, which is ample at size 12.

**Size.** `size = clamp(round(introduces / 8), 12, 24)`, where `introduces` counts the scope set. One
question per eight items taught, floored so a short topic still gets a real checkpoint and capped so no
test outgrows a ten-minute sitting. Measured: this puts almost every N5/N4 topic at 12 and the N3 topics
at 17–20, and **the pool covers the size for 48 of the 49 tested topics**; the one that does not on its
own items is `top:n3-revisao`, whose `range` scope resolves it.

**Mix.** Two rules, both derived from the topic rather than fixed:

1. *By item kind* — proportional to what the scope teaches, with a floor of 1 for each kind present:
   `n(kind) = max(1, round(size × introduces(kind) / introduces(total)))`, then trimmed or padded from
   the largest share until the counts sum to `size`.
2. *By question form* — at least one production item and at least one cloze or `sentence_build`; the
   rest retrieval. This is the lesson rule ("≥1 retrieval + ≥1 production", `validate_exercise_contracts`)
   applied one tier up, so a topic test cannot be twelve multiple-choice questions.

**Pool sources**, in priority order — selection over generation, per §1.2:

1. the topic's own lesson exercises whose `target` refs are inside the scope set (the field from §2 is
   what makes this a query);
2. exam-bank items keyed to scope items, level-clean and inside the topic's last lesson's
   `cumulative_known_set` (the `validate_exam_level_gate` rule, at an arbitrary lesson — the same port
   `examStudy.server.ts` already does for study mode);
3. deterministically minted cloze items over bank sentences whose tokens are all inside that known set,
   using `scripts/build_vocab_exercises.py`'s existing templates — only for scope items that rules 1–2
   cannot reach.

**Pass rule.** Named `TOPIC_PASS_V1` and **stored on the record**, so changing it is a new criterion
value and rows evaluated under the old one stay comparable — the same device `lesson_progress.mastery`
uses for `MASTERY_V1`, and for the same reason.

| parameter | default | why |
|---|---|---|
| `total` | **0.70** | a house number, stated as one |
| `per_kind_minimum` | **0.50** | mirrors the JLPT's two-condition shape — the total *and* every sectional minimum (`exam_scoring.md` §2) — without borrowing its figures, which are not ours to borrow |
| `min_items_per_kind_for_minimum` | **3** | a minimum over one or two questions is a coin flip, so the per-kind minimum applies only where the mix put at least three |

A pass is the total **and** every applicable per-kind minimum. A test whose mix could not place three
items in a kind reports that kind as `minimum_met: null`, never as met — the same rule
`exam_attempt.sections[].minimum_met` already carries for an untested scoring section.

## 4. `exercise_attempt` and the `mistake_index` view

### 4.1 The decision: a new runtime entity, not an extension of `lesson_progress`

**Decided: `exercise_attempt`, a new append-only runtime entity.** `lesson_progress` is not extended.
Four reasons, in order of weight:

1. **Attempts happen outside lessons.** A topic test, a placement probe and a practice-hub drill all
   produce graded answers about corpus items. Hanging them off `(user, lesson)` gives a topic test's
   answers no home, or forces a fake lesson id — the modelling mistake that makes an index nobody can
   query.
2. **`lesson_progress` is a row read on every screen.** It holds seven counters and a verdict. Putting
   an unbounded per-item answer list inside it turns a hot, small row into a growing document, which is
   the same argument `skill_state.recent_items` is capped at 10 for ("it is state, not a log, and a log
   of drilled items belongs nowhere near a row read on every queue build").
3. **`review_log` must not absorb it** (§4.2).
4. **The counters stay derivable.** `lesson_progress.exercises_attempted` / `_correct` / `score` become
   a `GROUP BY` over `exercise_attempt` rather than a second source of truth. They stay on the row as a
   cache — the `card`/`review_log` split, one tier down — and the invariant is stated in §4.5.

Address: `xat:<opaque>`, a fourth runtime namespace beside `usr` / `att` / `rev`. Opaque and unordered
on purpose; ordering belongs to `answered_at`, not to a key.

### 4.2 The FSRS interaction — the rule, stated as a firewall

**A graded exercise answer never writes a `review_log` row and never mutates a scheduling field of a
`card`.** Not `state`, not `stability`, not `difficulty`, not `due`, not `step`, not `reps`, not
`lapses`.

Why, in the terms `user_state.md` §3 already sets:

- `review_log` is the FSRS optimizer's **entire training set and the only asset in the runtime model
  that cannot be regenerated**. Its rows must be scheduled reviews with a defined `elapsed_days` and
  `scheduled_days`; a lesson exercise has neither — the card may not exist yet (it is minted at lesson
  completion, and the exercises are answered before that), and when it does exist the answer is
  typically not due.
- An exercise is **binary**. FSRS wants a 1–4 rating; collapsing to {Again, Good} discards the Hard/Easy
  signal and biases D and S in a direction nobody has measured.
- The map is **not injective**. A card is `(item, kind)`; an exercise targets 1–22 items (median 1,
  mean 1.77 on the hand-authored half) and
  a `matching` grid targets six at once. There is no single card for a wrong answer to land on.
- `review_log.source`'s own description already says FSRS-6 "models same-day reviews crudely, so
  same-day lesson drills must be distinguishable from queue reviews when training". Feeding it
  unscheduled binary answers is that problem, worse.

**Reconciling the existing `review_log.source` enum.** `lesson_drill` and `exam_sim` are *not* made dead
by this rule and they are not about exercises. They name the case where the app presents an **actual card
review** — the card UI, a 1–4 rating, a due card — inside a lesson or inside an exam session. That is a
review that happened to be surfaced elsewhere. An *exercise* is a different surface: a question with a
prompt, an answer key and an explanation, authored in the courseware. The two are distinguished by which
table the answer lands in, and after this unit that distinction is enforceable rather than conventional.

**The one sanctioned coupling, and it needs no schema change.** A wrong exercise answer changes what the
learner sees next by being a **ranking input to the queue builder**, not a scheduling input: among the
cards already due today, those whose item is weak in `mistake_index` are served first, and the daily caps
are untouched. The card stays a pure function of its `review_log`, so an FSRS-6 → FSRS-7 bump stays a
replay. The learner gets "I got it wrong, so it came back sooner"; the model gets nothing it did not
earn.

**And one bounded exception, flagged for W26's owner rather than assumed.** `mistake_index` MAY raise
`card.leech_state` from `none` to `flagged` (never to `suspended`, which is a learner or scheduler
action). That places `leech_state` in the same non-replayable class as `suspended_at` and `buried_until`
— `user_state.md` §3 names "the learner's own suspend/bury flags" as the exception to replay and does
not name `leech_state`. **This document does not edit that sentence**; it records that the sentence needs
one more field named in it, and until it is, the app must not write `leech_state` from this path.

### 4.3 The `mistake_index` view

**A view, not a table.** No schema file, no manifest row, no stored rows — it is a named query over
`exercise_attempt` joined to `card`, defined here so that two consumers cannot define it differently.

Parameters, named `WEAKNESS_V1` and stored on any materialization, for the `MASTERY_V1` reason:

| parameter | default | meaning |
|---|---|---|
| `window_days` | 90 | attempts older than this are not evidence |
| `half_life_days` | 14 | recency weight `w = 2^(−Δdays / 14)` |
| `min_evidence` | 2.0 | the summed weight below which an item has no verdict (`unknown`, never `weak`) |
| `weak_at` | 0.34 | weighted miss rate at or above which the item is `weak` |

```
mistake_index(user, item) =
  A = { exercise_attempt rows r : r.user_id = user
                                ∧ r.answered_at ≥ now − window_days
                                ∧ item ∈ { e.ref : e ∈ r.item_refs, e.role = "target" } }
  w(r)      = 2 ^ ( −(now − r.answered_at).days / half_life_days )
  evidence  = Σ_{r ∈ A} w(r)
  miss_rate = Σ_{r ∈ A, ¬r.correct} w(r) / evidence            (evidence > 0)
  state     = "unknown"  if evidence < min_evidence
              "weak"     if miss_rate ≥ weak_at
              "ok"       otherwise
```

The row the API returns carries the score **and its denominator** — `attempts`, `misses`, `evidence`,
`last_missed_at`, `first_missed_at` — because "you are weak at X" with no denominator behind it is the
claim `skill_state.reps`/`correct` exist to prevent.

**The memory track sits beside it, never inside it.** The view also returns, read through the item:
`card.state`, `card.lapses`, `card.leech_state`, `card.due` and `card.introduced_by`. They are
**evidence displayed next to the score, not terms in it** — the two tracks are deliberately separate
(`srs_design.md` §5, `user_state.md` §8), and averaging a lapse count into an exercise miss rate would
make both unreadable. `introduced_by` is what routes remediation: the lesson that taught it is the
thing to re-open.

**Cross-surface by construction.** Because every attempt carries `item_refs` and every surface writes
`exercise_attempt`, one query spans lesson exercises, topic tests, placement probes, drills and exam
items — which was the whole ask in `tests_exercises` G6 ("show me again what I got wrong" has no index
to run against: it would have to substring-match Japanese text).

### 4.5 What guards it

Runtime entities have no records to validate — `user_state.md` §13 says so plainly ("What is enforced
today is that the contracts exist, compile, resolve, and are honestly catalogued"). So the guard is in
three parts and the third is the only new machinery:

1. **`validate_contracts.py` + `validate_schema_generation_is_current.py`**, unchanged: the new schemas
   must declare `class: runtime`, must declare **no** `files` glob, must compile as Draft 2020-12, every
   `$ref` must resolve, and neither name may appear in `contracts/_shapes.json`. `build_schemas.py`
   fails if a `RUNTIME` file is missing.
2. **`validate_item_refs.py` check E** already guarantees that whatever an attempt copied was a real
   target when it was served.
3. **`scripts/validate/test_assessment_fixtures.py`** — a fixture suite, on the
   `test_review_apply.py` pattern, asserting the invariants JSON Schema cannot express, each with a
   plant:

| invariant | plant that must fail |
|---|---|
| `context.ref` prefix matches `context.kind` (`les:`/`asm:`/`att:`/null) | an `asm:` ref under `kind: lesson` |
| every `item_refs[].ref` in an attempt exists in the served question's own `item_refs` | an attempt naming an item the exercise does not target |
| **the FSRS firewall**: grading a fixture exercise produces zero `review_log` rows and leaves every `card` field byte-identical except `leech_state` | a grader that writes a `review_log` row |
| `lesson_progress.exercises_attempted` equals the count of `exercise_attempt` rows with that `(user, lesson)` and a distinct `question`; `_correct` likewise | a counter incremented without a row |
| for a submitted `exam_attempt`, the count of attempts with `context.ref = attempt_id` equals the number of `items[]` with a non-null `answer_given` | a paper graded without the answer stream |
| `mistake_index` under `WEAKNESS_V1` returns `unknown`, never `weak`, below `min_evidence` | a single miss reported as weak |

**The one deliberate duplication, stated once.** `exam_attempt.items[]` already stores per-item
`answer_given` / `correct` / `response_ms`, and an exam grading also appends `exercise_attempt` rows. The
duplication is kept on purpose: the paper record must stay **self-contained and reproducible** for
support months later (that is why `seed` and `presented_options[]` are stored at all), while the mistake
index must be **one query over one shape**. Making the index read a union of three differently-shaped
tables is how it does not get built. The invariant above is what stops the two drifting.

## 5. Placement

### 5.1 The item → lesson index

**Every placement question reduces to one join:** given a question, which lesson first makes it
answerable? Measured today over all 6,081 exam items, resolving in this order:

| resolved via | items | rule |
|---|---:|---|
| `vocab` slug → the lesson that unlocks it | 3,722 | the unlock ledger guarantees exactly one |
| `grammar` bare key → `gram:<key>` → its lesson | 728 | **the normalization the 73.7% audit was missing** |
| `reading` slug → `reading.gated_to_lesson` | 517 | W15 put `gated_to_lesson` on all 286 passages |
| the cited `sentence`'s own token dissection → the latest lesson among its tokens' items | 934 | this is what makes `sentence_order` placeable |
| **total** | **5,901 of 6,081 (97.0%)** | |
| unresolved | 180 | 173 listening items (no audio, excluded from every paper anyway) and 7 stragglers |

Add the 2,463 lesson exercises, each keyed to its own lesson by construction, and the 4,774 exercises
after the W20 apply. The index is therefore **derivable, complete enough, and already implied by data
the export ships**.

**Publish it as a generated map, not a second address space.** `course/item_lesson_index.json`,
`packing: "map"`, one entry per question id → `{lesson, level, via}`, regenerated by the exporter and
guarded by `validate_placement_index.py`, whose only real check is that it **re-derives byte-identically**
from `lesson.unlocks` + `reading.gated_to_lesson` + `corpus/sentences/bank.json`. It is a cache, in the
same class as `course/outline.json`, and it is a cache because a placement probe that has to load 322
lesson files to ask one question is a probe nobody ships. Ratchet: coverage may not fall below 5,901.

### 5.2 The mechanism

Placement runs at **topic granularity, not lesson granularity** — 52 topics, not 322 lessons. Per-lesson
placement is false precision: the median lesson introduces 7–18 items and no 30-question probe can
separate two adjacent lessons. Six adaptive rounds separate 52 topics (`log₂ 52 ≈ 5.7`), five items per
round, so the probe is **≤ 30 questions** and sittable in one go.

1. **The probe pool.** For each topic, its `topic_test.pool` (§3) already exists and is already scoped
   to that topic's items. Placement draws from it; no second pool is authored. The five pre-N5
   kana/method topics probe the kana registry directly (211 glyph records) instead.
2. **The search.** Binary search over topics in course order. A round at topic *T* draws 5 items from
   `test:<T>`'s pool under the sitting's seed; ≥ 4 of 5 correct moves the search later, ≤ 2 moves it
   earlier, 3 repeats the round once with fresh items and then moves earlier. Termination: the deepest
   topic *T\** the learner cleared.
3. **The entry point.** `entry_lesson` = the first lesson of the topic **after** *T\**, then walked back
   through `needs[]`: if any transitive prerequisite of that lesson belongs to a topic the probe did not
   clear, the entry moves to the earliest such prerequisite. This is why the prerequisite graph had to
   land first (W21) and why the re-derived numbers in §0 matter — the closure is real, mean 130.5
   ancestors and max 261.

   **One caveat the graph itself forces.** Seven of the eight roots are not pre-N5: they are
   `les:n5-desu-wa-01/02`, `les:n5-perguntas-02` and four `les:n5-numeros-tempo-*` lessons, at course
   positions 41–60, whose derivable edges came only from their own family (the pattern W21 named for
   the 41 kana lessons). A placement that lands inside `top:n5-numeros-tempo` therefore has almost no
   prerequisite closure to walk back through, and the topic ordering carries the whole decision there.
   That is a course-data gap, not a placement bug — it belongs to W21b, and until it closes the probe
   must not treat "few ancestors" as "nothing missing".
4. **The skipped set.** Every lesson strictly before `entry_lesson` in course order. `lesson_progress`
   rows are written for them with `status: "completed"`, `attempts: 0`, `score: null`,
   `mastery.state: "unknown"` — the honest values: the learner did not sit them, and no criterion was
   evaluated. `mastery` is deliberately **not** set to `met`: `unknown` "is NOT the same as not_met" and
   it is not the same as met either.
5. **The cards** — this is the D2 half, §5.3.
6. **Reversal.** Placement is undoable: delete the synthesized `lesson_progress` rows and the cards
   tagged `placed-out` (no `review_log` row exists for a card that was never reviewed, so nothing is
   orphaned). A learner who placed too high walks back with no residue. This is a property of the design
   and it is why nothing in step 4 writes a `mastery` verdict.

### 5.3 D2 — the options, and the default

D2 asks two things (`APP_PLAN` §4): what "lesson complete" means, and the placement policy (score →
entry; does placing out seed cards?). **Both stay the owner's.** What this document owes is that either
answer is implementable without a schema change, and it is: every field either answer needs already
exists.

**D2(i) — what "complete" means.**

| option | what it does | field that records it |
|---|---|---|
| **(a) default ▸** `status` and `mastery` stay independent: `completed` = the learner reached the end of the lesson and attempted every exercise once; `mastery` is evaluated separately under `MASTERY_V1` | keeps "what the learner did" separable from "what the data says", which is the case the criterion exists to find | `lesson_progress.status`, `lesson_progress.mastery.state` — both already contracted |
| (b) `completed` requires `mastery.state = met` | a WaniKani-shaped gate | same two fields; the change is a rule, not a column |
| (c) per level | N5 lenient, N3 strict | a new `criterion` value (`MASTERY_V2`) — already the contracted way to change it |

This document adds one thing to (a): **the topic test, not the lesson, is where a gate belongs.** A
lesson is a teaching unit; a topic is the unit a learner would re-sit. `topic_test.pass_rule` is
therefore the natural home for a progression gate whichever way D2(i) goes, and it is on the record
rather than in a query.

**D2(ii) — does placing out seed cards?** The measured stakes: a learner placing into the middle of the
course skips **130.5 lessons on average** (max 261 by prerequisite closure), which is up to ~2,000 vocab
records plus kanji and grammar.

| option | what happens | cost, measured |
|---|---|---|
| (a) **do not seed** — `cards_seeded: false` on every skipped lesson | the SRS never carries the placed-out material | a learner who placed into N4 never reviews a single N5 word. The memorization promise — the product's second pillar — is void for everything before the entry point |
| (b) **seed as `new`, untagged** | every skipped item enters the new-card queue | `user.scheduler.daily_new_cap` is **10**. 2,000 placed-out cards is a **200-day backlog** of "new" cards for material the learner demonstrably knows. This is the exact failure `cards_seeded`'s own description names ("the daily new-card cap gets spent on material the learner demonstrably already knew") |
| **(c) default ▸ seed as `new`, tagged `placed-out`, admitted under a separate cap** | the cards exist and are schedulable; the queue builder admits `placed-out` cards under `placement_new_cap` instead of `daily_new_cap`, so they do not compete with the material the learner is actually learning | uses only fields that already exist: `card.tags` (contracted, "deliberately NOT an enum: the learner-added half is open by construction") and `lesson_progress.cards_seeded`. The cap is an app policy number, not a schema field |

**Default marked: (c).** It is the only option that keeps the memorization promise without spending the
new-card budget on known material, and it costs no schema change. And critically, **(a) and (c) differ by
one boolean per lesson**: `cards_seeded`. Choosing (a) later is running the placement apply with seeding
off; choosing (c) after (a) is minting the cards. Neither is a migration. That is the property the task
asked for and it is why the seeding decision was *not* encoded anywhere structural.

**What is deliberately not proposed:** seeding placed-out cards directly into `state: "review"` with a
synthesized stability. It reads well and it is wrong twice — a card in `review` with no `review_log`
behind it breaks the replay property that makes an FSRS version bump a replay (`user_state.md` §3), and
writing synthetic log rows to fix that poisons the optimizer's training set with reviews that never
happened.

## 8. What this document does not deliver

- **The D2 answer.** §5.3 lays out both halves with a default marked and proves both are implementable
  from fields that already exist. It stays the owner's.
- **`exam_item.item_refs` populated.** W18 regenerates the banks once; authoring a field onto 6,081
  items that are about to be rebuilt is the waste-ledger mistake this plan exists to avoid.
- **The 39 authored `item_refs` rows.** Measured and scoped here (§2.4); one agent, one verifier, in the
  apply unit.
- **The queue builder's ranking rule.** §4.2 says a wrong answer ranks rather than schedules; how many
  ranked cards a session admits is app policy and belongs with the D8 work.
- **`user_state.md` §3's replay sentence.** §4.2 records that `leech_state` needs naming there beside
  the suspend/bury flags. This document does not edit that file.
- **Mid-level checkpoints beyond the topic test** (`jlpt_course_path` G11's second row). A test per topic
  *is* a checkpoint every topic; whether the app surfaces one every three or four topics instead is a
  courseware decision, not a schema one.
- **Any validator over runtime records.** There are none. §4.5 says what can honestly be enforced
  instead, and enforces that.
