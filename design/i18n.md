# Localization model — language-agnostic internals, content as locale modules

> **STATUS: APPLIED 2026-06-14 (Option A).** `localized_text` is live (migration 004); all authored content
> (6,937 rows) moved to it under locale `pt-BR`; exporters/persisters/validators use neutral field names via
> `scripts/ingest/i18n_text.py`. The legacy `*_pt` columns are **vestigial (NULLed), deprecated** — a future
> migration may drop them; fresh rebuilds leave them empty and use `localized_text`. Adding a locale now = new
> rows, no schema change.


> Owner directive (2026-06-14): the **internal layer** (schema, identifiers, file/dir names, code, enum/type
> values, keys) is **English and language-neutral**. Only **content** (translations, meanings, explanations,
> lesson text, labels, names, descriptions) is localized. **Portuguese (pt-BR) is the only locale for now**,
> but it is a **locale module** — more languages can be added later with **no structural change**.
> **Plan now; apply as a PRE-P5 task** (before mass production, so we don't generate thousands of rows in a
> PT-bound shape and then have to migrate them).

## Principles
- **Identifiers / enums / keys → English, neutral.** e.g. `<note type="l1-pitfall">` (not `armadilha-pt`);
  "L1" = the learner's native language (currently pt-BR), never hard-coded as "pt" in structure.
- **Content → localized**, conceptually keyed by a `locale` tag (`pt-BR` today; `es-LA`, `en-US`… later).
- **Locale dimension, not a schema axis.** Adding a language = adding content rows for that locale, never a
  schema change — the same future-proofing as the corpus's level-agnostic rule (§1.6).

## Current state (PT-bound — to migrate)
The corpus schema currently uses PT-suffixed columns that are really "the pt-BR locale":
`meanings_pt` (kanji), `gloss_pt`/`notes_pt` (vocab senses), `label_pt`/`explanation_pt`/`formation_pt`/
`nuance_pt` (grammar), `pt`/`pt_literal`/`structure_explanation_pt` (sentence), `role_pt`/`gloss_pt`/
`conjugation_note_pt` (token), `function_pt`/`explanation_pt` (particle), family
`label_pt`/`description_pt`/`governing_rule_pt`, topic `objectives_pt`, module `overview_pt`, lesson `body`/
objectives. The lesson format's `<note>` enum has already been de-PT'd (`l1-advantage`/`l1-pitfall`).

## Migration options (pick one in the pre-P5 task)
- **A — `localized_text` table (recommended):** `(entity_type, entity_id, field, locale) → text`. Registries
  keep language-neutral fields; PT rows seeded from the current `_pt` columns; app/exports join by active
  locale. Cleanest for many languages.
- **B — neutralize columns in place:** rename `_pt` → neutral field names with a `locale` column / per-locale
  rows, or store each field as JSON `{locale: value}`. Lighter, less normalized.

Write the migration, move existing PT content into the locale form, re-export. Identifiers, file names, and
exports stay English; only the text values are locale-scoped.

## Why pre-P5
Doing it now delays the heavy lift; doing it after bulk generation means migrating thousands of rows. So the
**first task when mass production resumes** is this migration — then all P5/P6 content lands locale-aware.

**Already satisfied (Layer-A facts).** The export's locale-object shape is `{"pt-BR": <ours>, "en": <Layer-A

- kanji **meanings** → `en` from KANJIDIC (now populated for N5→N1, incl. the N2/N1 banks).

course, topic, lesson, exercise text** — those stay pt-BR-only (they are the localized product surface; an
English *course* is a separate future product, not a cross-reference asset).

**How:** a future `en`-generation pass over the corpus Layer-B fields → store under `localized_text` locale
`en` → exporters already emit the `en` key, so detail pages/exports can show or diff pt-BR ↔ en. Tracked in
[`product_roadmap.md`](product_roadmap.md).

# Locale scope table (W40, 2026-09-02)

> **Why this exists.** Until now the scope of "the corpus layer is bilingual" was a prose sentence in the
> section above, and it named grammar, families, sentences, tokens and particles while saying nothing about
> kanji reading notes, kana family labels, capability names or the speaking path. The readiness audit
> (`research/reports/readiness/platform_contract_i18n.md` §2.3) found ~10.7k locale fields with no `en` and
> could not say which of them were defects. This table is the answer, and it is the **input to
> `validate_locale_parity.py`**: a required row with a missing `en` is a failure, an optional row never
> fails, and a row naming a field that no longer exists is a failure too.

## The rule

- **`en` is REQUIRED** where `en` is the **Layer-A anchor** (the English is the source and the pt-BR was
  derived from it), or where **a second locale would translate FROM it** — i.e. any corpus-layer registry
  field, because the registries are what a future locale module is built against.
- **`en` is OPTIONAL** where `en` would itself be a translation of **pt-BR-only pedagogy** — the courseware
  product surface (course / topic / lesson / exercise / speaking path), which this file has excluded since
  2026-06-25. Optional means *never a failure*, not *never present*.
- **Not a locale object** is a third state and it is tracked here too: a learner-facing string that is a bare
  `string` in the contract. For those, adding a locale IS a schema change, which is the one place the
  project's "adding a language adds rows, never structure" claim does not hold today.

# `en_layer` — the shape (W40, decision D-shape)

## What the field has to say

Measured over the export and `db/corpus.sqlite`, 2026-09-02:

| where the `en` comes from | layer | count |
|---|---|---:|
| `sentence.en` column (Tatoeba / JEC verbatim) | **A** | 3,529 |
| `localized_text` row `(sentence, id, 'translation', 'en')` | **B** | 2,342 |
| neither | — | 18 |

Overlap between the two sets: **0**. Union: 5,871 — exactly the number of `translation.en` keys in
`corpus/sentences/bank.json`. `provenance.jp_source` is **not** a usable proxy: 135 Tatoeba-sourced
sentences carry a derived English, because those 135 have no `lang='eng'` pairing upstream at all.

## Where it appears: `sentence.translation` and nowhere else

This is the load-bearing measurement, and it is what makes the cheap shape sufficient. Of the 44
locale-object field paths in the export, **exactly one mixes layers**:

- Every `localized_text` row with `locale='en'` is `layer='B'`. All 15 `(entity_type, field)` pairs, 109,976
  rows, **zero exceptions**.
- The three Layer-A registry fields (`kanji.meanings`, `vocab.senses[].gloss`,
  `kanji.example_words[].gloss`) are 100% A by construction: the exporter reads a dedicated column
  (`kanji.meanings_en`, `vocab_sense.gloss_en`) with **no `localized_text` fallback**, so there is no code
  path by which a derived value can enter them.
- `sentence.translation` is the only field whose exporter line coalesces two sources —
  `export_corpus.py:517`, `loc(pt=…, en=s["en"] or SLen.get((sid, "translation")))`.

So the layer of every other `en` in the corpus is a **constant per field path**, and a constant belongs in
the scope table above (the `en_layer` column), not in 134,904 copies inside the JSON.

## Recommendation: (a) the sibling map. Adopt it.

- **Field:** `translation_layer`, a sibling of `translation` on the `sentence` record.
- **Shape:** an object keyed by locale, values from the existing `Layer` enum in
  `contracts/common.schema.json` — `{"en": "A"}` or `{"en": "B"}`.
- **Presence:** optional; emitted only on `sentence`, only when `translation` has an `en` key.

**Why not (b), per-locale `{value, layer}` objects.** (b) changes the *type* of `LocaleText` and
`LocaleTextList`, and therefore of **all 175,119 locale objects** and every consumer of them:
`contracts/types.ts`, the prototype's renderers, the 39-gate validator suite,
`audit_hygiene_all_locales.py`'s ~244k-string walk, `scripts/ingest/i18n_text.py`, and every future exporter.
That is a whole-corpus type migration to express a distinction that is real in **1 of 44 field paths**.

**Can (b) express anything (a) cannot?** I looked for one and did not find it.

- *Different layers for `pt-BR` and `en` on the same string* — the actual case here
  (`sentence.translation`: pt-BR is B, en is A). A locale-keyed map handles it natively:
  `{"pt-BR": "B", "en": "A"}`. Not a discriminator.
- *A third locale later* — the map takes a key: `{"en": "A", "es-LA": "B"}`. Not a discriminator.
- *Per-item layer inside a `LocaleTextList`* — the one thing a per-locale wrapper genuinely cannot reach.
  But (b) is also per-locale, not per-item, so it cannot reach it either. Measured: no such mixing exists
  (`meanings_en` is one column value per record, 100% KANJIDIC). Not a discriminator.

No concrete reason for (b) was found. **Recommend (a).**

**One correction to the APP_PLAN shorthand.** `research/reports/APP_PLAN.md` W40 writes the default as
`en_layer: "A"|"B"` — a bare scalar. Adopt the **map** instead, under the name `translation_layer`. The
scalar cannot state what layer `pt-BR` is, and it needs a second field the day `es-LA` arrives. The map costs
the same bytes today (`{"en":"A"}` against `"A"` is nine characters) and costs nothing later. Decision A7 is
unchanged; only the spelling is.

## Enum owner

`Layer` in `contracts/common.schema.json#/$defs/Layer` — `["A","B","C"]`, already defined, already
documented, already used by `reading`, `exam_item`, `exercise_*` and `speak_*`. `translation_layer` `$ref`s
it. **No new enum is created by W40**, and `"C"` is legal in the type but must never appear in
`translation_layer` (rule R6 rejects it): a translation is evidence or a sibling, never pedagogy.

One new `$defs` entry is added for the container shape:

```jsonc
"LocaleLayerMap": {
  "type": "object",
  "description": "Per-locale provenance for the sibling LocaleText field named by dropping `_layer`. Present only where a field's layer varies per record; where it is constant for a field path, the constant is recorded in design/i18n.md's locale scope table instead of being repeated in every record. A key here MUST have a matching key in the sibling LocaleText.",
  "additionalProperties": { "$ref": "#/$defs/Layer" },
  "minProperties": 1
}
```

## Exporter rule — a spec for the W40 apply step, not an implementation

In `scripts/export/export_corpus.py`, in the sentence loop, immediately after the `translation` line
(currently `:517`). The rule reads the two storage locations **separately** instead of coalescing them, and
leaves the existing `translation` line exactly as it is so no consumer breaks.

```
anchor  := sentence.en column, non-NULL and non-empty after strip
derived := localized_text row (entity_type='sentence', entity_id=sid, field='translation', locale='en')

if anchor:      translation_layer = {"en": "A"}
elif derived:   translation_layer = {"en": "B"}
else:           omit the key entirely
```

Hard invariants the apply step must hold, each one checkable:

1. `translation_layer` is emitted **iff** `translation` has an `en` key. Never one without the other.
2. `translation` itself is byte-identical before and after. W40 adds a key; it changes no value.
3. Expected census on the current data: **3,529** `{"en":"A"}` + **2,342** `{"en":"B"}` + **18** absent
   = 5,889 sentence records. Any other split means the rule was implemented wrong, not that the data moved.
4. `anchor` and `derived` are checked in that order and are known-disjoint (overlap 0 today). If a future
   record has both, `"A"` wins and `validate_locale_parity.py` reports it as a data defect, because a record
   holding two Englishes has an unreviewed duplicate.
5. `pt-BR` is **not** given a key. Its layer is a constant `B` for this field (`localized_text`: 5,889 rows,
   all `layer='B'`), and that constant lives in the scope table.
6. No other entity gains a `*_layer` sibling in W40. If a future field starts mixing, the scope table's
   `en_layer` column changes from a constant to `per-record`, and that edit is what authorizes the new
   sibling — never the other way round.

**Plant proof for the exporter rule** (required by APP_PLAN §1 before this joins the suite): on a copied
tree, `UPDATE sentence SET en=NULL` for one anchored slug that also has no `localized_text` en row, then
re-export. That record must lose both `translation.en` and `translation_layer`, and the census must read
3,528 / 2,342 / 19. Restore, then null a slug that *does* have a `localized_text` en row; it must flip to
`{"en":"B"}` with the census reading 3,528 / 2,343 / 18.

# `validate_locale_parity.py` — validator spec (build in the W40 apply step)

**Input: the two scope tables above, parsed from this file.** Not a generated sidecar JSON. Two files means
drift, and drift in the file that defines what "complete" means is the failure mode this validator exists to
prevent. The tables are parsed as GitHub pipe tables under the headings
``## Corpus layer — `en` REQUIRED`` and ``## Courseware layer — `en` OPTIONAL``; the column contract is
`entity | field | learner-facing | en required | carries en today | [en_layer |] backfill route`, with the
`en required` cell matched case-insensitively on its leading word, `yes` or `no`. The exemption ids are
parsed from the `### The 18 …` subsection by their `sent:` slugs. A parse failure is a validator failure,
never a skip.

**Entity → file resolution** comes from `contracts/manifest.json` (`files` glob plus `packing`), so the
validator never hardcodes a path. **Field paths** use the export's own dotted form with `[]` for arrays
(`sentence.tokens[].gloss`), which is how the measurement above was produced and is therefore already known
to resolve against real data.

## Rules

| id | rule | failure |
|---|---|---|
| **R1** | A row marked **required**: every instance of that field must have a non-empty `en`. | FAIL, listing entity, field, and the first 20 offending record ids. Suppressed for an id in the row's exemption list. |
| **R2** | A row marked **optional**: never fails, whatever the coverage. Reported as INFO with the measured percentage, so drift is visible without being a gate. | never |
| **R3** | **Stale scope row.** A row whose field path yields **zero non-null instances** across the entity's files. Same class as a stale exemption file: the table asserts a field exists and it does not. | FAIL. Fires today on `kanji.notes`, `family.description` and `family.members[].note` — which is the point; the apply step must resolve all three before the gate can go green. |
| **R4** | **Undeclared field.** A locale object found in the export at a path with **no** row in either table. | FAIL. This is the rule that would have caught `kanji.readings[].note` sitting outside the scope statement for months, and it is what makes the table's completeness enforced rather than aspirational. |
| **R5** | **Shape.** Every locale object's key set must be a subset of the declared locale set (`pt-BR`, `en`), and `pt-BR` must be present. | FAIL. Zero violations today: the export contains exactly two key sets, `{pt-BR}` on 32 field paths and `{pt-BR,en}` on 20. |
| **R6** | **`en_layer` integrity.** Where a row's `en_layer` is `per-record`: every instance with an `en` key carries the sibling `<field>_layer`, its keys are a subset of the instance's own locale keys, its values are in `Layer`, and `"C"` is rejected for a translation. Every instance *without* an `en` key must **not** carry the sibling. Where `en_layer` is a constant, the sibling must be **absent** from every instance. | FAIL |
| **R7** | **Exemption liveness.** Every id in a row's exemption list must still resolve to a record, and that record must still lack `en`. An id that has since gained an `en`, or that no longer exists, is a stale exemption. | FAIL |

## Ratchet

The required-en gap is 10,514 today and W40's design step does not close it — the backfill campaign does. So
the validator ships with `research/reports/locale_parity_baseline.json`, a per-field allowed-miss count
(`{"kanji.readings[].note": 3679, "sentence.tokens[].role": 1796, …}`), and R1 fails only when a count
**rises above** its baseline. Per APP_PLAN §1 the ratchet may only shrink: the backfill drives each entry to
0 and deletes it, and a baseline entry for a field at 0 misses is itself a failure (a stale ratchet row, the
same class as R3 and R7). R3 through R7 have no ratchet and are hard from day one — all currently green
except R3's three dead rows.
