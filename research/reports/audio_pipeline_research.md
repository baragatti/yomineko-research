## 0. Answer in five lines

1. **Model:** Chatterbox Multilingual **V3** (Resemble AI, released 2026-06-10, 0.5B Llama backbone,
   MIT). It covers `ja` and `pt`, and ships a dedicated **pt-BR Language Pack** finetune. Every output
   carries the PerTh watermark and it cannot be turned off.
2. **Japanese is the weak spot:** Resemble's own CER for Japanese is **21.87%**, which they call
   "usable with caveats" (pt-BR: 0.35%). Chatterbox turns kanji into hiragana with **pykakasi**, a
   dictionary converter with no context. **We should feed it our verified readings (kana) and not
   kanji.** Its own code passes kana through unchanged, so doing this removes the reading-error
   class completely.
3. **GPU path:** native Windows with **AMD's released ROCm 7.2.1 PyTorch wheels** (torch 2.9.1,
   Python 3.12, Adrenalin ≥ 26.2.2). The fallback is WSL2 **Ubuntu 24.04** with ROCm 7.2.1. Avoid the
   7.14 preview wheels: an open issue reports silent all-zero tensors on gfx1201 under Windows.
   DirectML is at end of life. ZLUDA is unnecessary.
4. **Volume:** tier 1 (pre-N5/N5/N4 as the learner meets them) is **5,807 distinct Japanese units /
   65,665 chars** plus **655,080 chars of pt-BR lesson narration**. That is about 16 h of audio, and
   pt-BR is roughly 80% of it. Everything including N3 and the unreferenced bank comes to about 29 h.
5. **Throughput is unmeasured on this card.** No public benchmark for a 9070 XT exists. A 200-unit
   pilot has to measure it, and the same pilot has to measure Japanese intelligibility, before the
   full run is scheduled.

### 1.1 How Chatterbox reads Japanese (the finding that shapes the design)

`MTLTokenizer.encode` sends `ja` text through `hiragana_normalize` (source:
https://raw.githubusercontent.com/resemble-ai/chatterbox/master/src/chatterbox/models/tokenizers/tokenizer.py).
The function runs `pykakasi.kakasi().convert(text)` and handles each segment in one of three ways:

- **contains a kanji** → replaced by pykakasi's `hira` (a leading は/へ gets a space in front);
- **all katakana** → kept as katakana;
- **anything else** (hiragana, digits, punctuation) → **kept verbatim**;

and then applies NFKD to the whole string.

What follows from this:

- **The model never sees kanji.** Two headwords with the same reading (橋/箸) are the same input to
  the model, so the model has no way to render different pitch patterns for them.
- **pykakasi supplies every kanji reading, and it does so from a dictionary with no morphological
  context.** Its segmentation is known to be weak (for example
  https://github.com/miurahr/pykakasi/issues/114, 2020, kanji + っ mis-segmented). Our corpus already
  holds **verified per-token readings** (SudachiPy + checks, `tokens[].reading`). If we send the
  reading in hiragana, `hiragana_normalize` passes it through untouched and pykakasi drops out of
  the loop. This is the "reading hint" D3 asked about, and in practice it is a full replacement
  for pykakasi, not a hint.
- **Digits are passed through as digits**, and pykakasi does not read them. The bank's verified
  tokens already carry correct counter readings: 339 bank sentences contain digits, and all 384 of
  their digit tokens have a kana reading (measured: `６日` → むい+か, `１０日` → とお+か, `四月` →
  しがつ). Resolving digits through the token reading removes the number risk that Resemble's own
  tracker shows for another language (https://github.com/resemble-ai/chatterbox/issues/287, zh, 2025-09-17,
  open: "Numbers are mis-pronounced or skipped").
- **Particles:** our token readings are phonetic (particle は has reading わ on 5,345 of 5,346 tokens).
  The design keeps the **surface** of every kana token, so は stays は. That matches the orthographic
  text the model was trained on after pykakasi, and the context-level は/わ question does not arise.
- **Pitch accent cannot be controlled.** Nothing in the input carries accent. The corpus has kanjium
  pitch data for 637/709 N5 and 582/653 N4 vocab. Chatterbox audio will show whatever accent the
  model produces, so the audio cannot be used to *teach* pitch (learning_guidelines line 57). See §5.

The 21.87% CER is measured against the kanji source text with a generic ASR. Part of it is
probably orthographic mismatch (whisper writing a word in kana that the source wrote in kanji), and
part is real reading error that kana input removes. Our number is unknown until the pilot measures
it on **kana-normalised** comparison (design §7).

Known traps on path A:

- **Headless dGPU crash.** `torch.cuda.is_available()` hits an access violation in `amdhip64_7.dll`
  (ROCm 7.2.1, torch 2.9.1, Windows build 26200 — the owner's build) when the 9070 XT is installed
  but the monitor is on the iGPU. The workaround is to plug the display into the 9070 XT.
  https://github.com/ROCm/legacy-rocm-build/issues/6458 (2026-07-17).
- **Multi-GPU enumeration.** #8379 ran on `cuda:1`, with an iGPU also visible. Pin the dGPU with
  `HIP_VISIBLE_DEVICES`, which the voicebox guide recommends for iGPU systems, and gate every run
  on a numeric smoke test (design §8).
- **Chatterbox pins torch 2.6.0.** Install it with `--no-deps` and supply the other dependencies
  by hand. Otherwise pip replaces the ROCm torch with a CUDA or CPU build.
- A third-party Chatterbox server says "ROCm only supports Linux" and runs RDNA4 through Docker
  with `TTS_BF16=on` (~40% throughput, their claim; https://github.com/devnen/Chatterbox-TTS-Server).
  That text predates AMD's Windows wheels. The bf16 hint is worth testing in the pilot.

**Recommendation: path A pinned to the 7.2.1 release, with path B (a new Ubuntu 24.04 WSL distro)
as the fallback if the smoke test fails.** Path A involves no VM or file-system hop, and the audio
store sits on NTFS next to the repo. The 7.2.1 wheels are an AMD *release* and not a preview. Exact
steps are in design §8.

### 2.1 Throughput and VRAM (estimates, to be replaced by the pilot's numbers)

- **No public Chatterbox benchmark for a 9070 XT was found.** The only AMD figure is an RX 7700 XT
  (gfx1101, Docker `rocm/pytorch`, `HSA_OVERRIDE_GFX_VERSION=11.0.1`, first Chatterbox release) at
  **11.2 s compute per 1 s of audio** on a 2.5 s clip, 2024-12-07
  (https://gist.github.com/danielrosehill/33575cb99efb05df801374ceb828731a). Treat it as a
  worst-case floor: an older card, an emulated gfx target, and a very short clip dominated by fixed
  overhead.
- A widely read V3 guide deliberately quotes no VRAM or latency numbers "because the ones floating
  around are unverified" (https://localaimaster.com/blog/chatterbox-multilingual-v3, 2026-07-20).
- **Planning assumption** (mine, not sourced): real-time factor 0.5–2.0 wall-s per audio-s at fp32,
  plus 30% retakes, plus the ASR check. For tier 1 (~16 h of audio) that is **~10–42 GPU hours**,
  which fits in overnight batches. The pilot measures the real figure.
- **VRAM (estimate):** the T3 checkpoint is ~2.1 GB in fp32 (pt-BR pack file size), and S3Gen plus
  the voice encoder add a small amount on top. Whisper-large-v3 for QA is ~3 GB in fp16. One TTS
  model plus the ASR fits 16 GB with room to spare. Load the `ja` (V3 base) and `pt-BR` (pack)
  models in separate runs, not together.

about 3 GB. There are 194 GB free.

## 4. Licence and voice consent (commercial app)

- Code and weights are MIT, which puts no restriction on the audio we generate. The watermark
  stays in every file. That is compatible with commercial use, and it gives us a built-in way to
  disclose AI audio. **Recommend stating "voz sintética" in the app credits** and not hiding it.
- **The reference voice is the real licensing question.** Cloning a person's voice needs that
  person's written consent, and the consent has to cover synthetic reuse in a paid product. Voice
  can be treated as personal data under LGPD, so the consent record needs to exist before the first
  clip. Do not clone voices taken from research corpora or from Tatoeba contributors. **Record
  native speakers** (JP: F1, M1, plus F2, M2 and N for listening; pt-BR: one narrator) with a
  signed consent form, and keep the clips and consent outside git (design §5).
- Tatoeba native clips: usable only per clip, where that clip's licence allows commercial use
  (ATTRIBUTION.md line 61). This is the 1.2 "selection over generation" route for 107 t1 sentences.

## 5. Risks and what the pilot must answer

| Risk | Why it matters | Pilot measure / fallback |
|---|---|---|
| Japanese intelligibility (Resemble's CER 21.87%) | wrong audio teaches wrong Japanese, and nobody reviews it before the MVP (owner D4) | ASR round trip on kana; pass rate ≥ 95% within 3 takes, otherwise the failing kind moves to a fallback engine |
| Short inputs (single kana, 1–2 mora words) | autoregressive TTS is least stable on tiny inputs (a risk to test, not a documented Chatterbox fact) | measure on 20 kana + 50 words; **fallback: record the 211 kana by hand** (a few minutes of a native speaker) |
| Pitch accent uncontrollable | whatever accent the model produces is what the learner imitates; homophones sound identical | do not attach pitch-teaching claims to TTS audio; minimal pairs (はし/はし) need human or accent-controllable audio (VOICEVOX-class engines take accent input; licences are per character: listening.md line 77) |
| ROCm on Windows correctness (#8379) | silent zeros would produce silent or garbage audio at scale | smoke test gates every run; the ASR check catches garbage per clip |
| Watermark | inaudible per Resemble; survives Opus | none needed |
| pt-BR numbers, abbreviations and Japanese inside narration | an "N5" or "〜てください" read by the pt voice sounds wrong | inline `<jp>` runs are voiced by the ja voice as their own units (design §6); pt number/abbrev normalisation rules are decided after pilot listening |
